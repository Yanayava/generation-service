# Сервис генерации

Сервис принимает заказ, списывает токены и ведёт задачу по цепочке провайдеров. Отказ провайдера — следующая нога. Отказ всех — один возврат. Начисление и возврат не повторяются, сколько бы раз ни пришёл вебхук и сколько бы процессов ни обслуживало запрос.

Как это устроено и почему — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Запуск

Нужны Docker и Python 3.11+.

```powershell
docker compose up --build -d
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
pytest
```

`docker compose up` поднимает PostgreSQL, сервис в четырёх воркерах и обоих фейковых провайдеров (`alpha` и `beta` — один процесс, два имени). Миграции накатываются при старте сервиса, до воркеров.

Проверка:

```powershell
docker compose ps
curl http://localhost:8000/health
```

Остановить: `docker compose down`. Вместе с данными: `docker compose down -v`.

Секрет вебхуков в стенде — `dev-secret`. Подпись заголовка `X-Signature` — hex HMAC-SHA256 сырого тела.

Оплата, которая создаёт пользователя и кладёт 100 токенов:

```powershell
$body = '{"payment_id":"pay-1","user_id":"00000000-0000-0000-0000-000000000001","tokens":100,"status":"succeeded"}'
$sig = python -c "import hmac,hashlib,sys; print(hmac.new(b'dev-secret', sys.argv[1].encode(), hashlib.sha256).hexdigest())" $body
curl -X POST http://localhost:8000/webhooks/payments -H "Content-Type: application/json" -H "X-Signature: $sig" --data $body
```

Дальше `POST /generate` с `user_id`, `model_slug`, `prompt`, `ref_images`. Ответ — `task_id`. Статус: `GET /tasks/{id}`. Баланс и журнал: `GET /users/{id}/balance`.

Начисляет только статус оплаты `succeeded`. Повтор того же `payment_id` деньги не двигает: побеждает первая доставка.

Поведение провайдеров для ручной проверки — `PUT http://localhost:8001/{alpha|beta}/settings`. Поля: `fail_rate`, `error_type` (`technical`, `moderation`, `payload`), `sync_mode` (`ok`, `503`, `timeout`), `webhook_count` (`0` — тишина, `2` — повтор), `duplicate_mode` (`sequential` или `concurrent`), `webhook_delay_seconds`. Без явной задержки вебхук уходит через случайные 2–20 секунд.

Каталог лежит в первой миграции.

| Модель | Цена | Ноги |
| --- | --- | --- |
| `image-fast` | 2 | `alpha` до 4 референсов, затем `beta` до 10 |
| `video-long` | 25 | `beta` до 2, затем `alpha` до 1, у `alpha` стоит `skip_on_moderation` |

Не хватает токенов — `402`. Уже три задачи в `dispatching` или `waiting` — `429`. Ни одна нога не принимает столько референсов — `400`, и журнал в этом запросе не меняется.

`4xx` от провайдера считается отказом `payload`: тело неправильное, следующая нога его тоже отвергнет. `5xx` и обрыв по таймауту клиента — `technical`, идём дальше.

## Тесты

`pytest` ходит в уже поднятый стенд, в ту же базу. Отдельная тестовая схема не нужна: каждый тест берёт своего пользователя.

Обязательные сценарии — `tests/test_required.py`:

1. 20 одновременных одинаковых оплат дают одно начисление.
2. 10 одновременных `failed` на последней ноге дают один возврат.
3. Отказ первой ноги: задача завершается на второй, в истории две попытки. Успешный вебхук второй ноги при этом приходит дважды и одновременно.
4. Поздний `completed` после сторожа не отменяет возврат и не записывает результат в задачу.

Четвёртый тест ждёт `PROVIDER_TIMEOUT` в 60 секунд и ещё около десяти, пока файл всё-таки придёт. Весь прогон занимает примерно две минуты.

Рядом лежат правила, которые иначе остаются невидимыми: `400` до списания, `402`, четвёртый параллельный заказ, `skip_on_moderation`, `payload`, чужая подпись.

## Миграции

Схема — ревизия `0001_initial`. Контейнер применяет её сам:

```text
alembic upgrade head
```

Локально против базы из compose та же команда. В `DATABASE_URL` для приложения стоит драйвер `asyncpg`, Alembic сам подменяет его на `psycopg`.

Следующая миграция не правит первую. Из корня репозитория:

```powershell
alembic revision -m "add generation kind"
```

В новом файле в `alembic/versions/` заполняются `upgrade` и `downgrade`. Накат снова `alembic upgrade head`: на чистую базу пройдут обе ревизии, на уже поднятую — только новая. Откат последней — `alembic downgrade -1`.

## Ровно один раз

Баланс не правят из приложения. Его меняет триггер `AFTER INSERT` на `ledger_entries`, в той же транзакции, что и строка журнала. `CHECK (balance >= 0)` держит баланс неотрицательным. Подтверждённый снимок базы поэтому всегда сходится: сумма журнала и есть баланс, операции без строки нет.

У строки уникальный `idempotency_key`:

| Движение | Ключ |
| --- | --- |
| Списание | `charge:{task_id}` |
| Возврат | `refund:{task_id}` |
| Оплата | `payment:{payment_id}` |

Повторная вставка с тем же ключом не создаёт строку, триггер не срабатывает, баланс стоит. Оплата дополнительно проходит через первичный ключ `payments.payment_id`: из пачки одинаковых вебхуков вставку выигрывает один, и только он, при статусе `succeeded`, пишет `topup`.

Возврат вставляется в той же транзакции, которая переводит задачу в `failed`. Десять параллельных `failed` выстраиваются в очередь на `SELECT ... FOR UPDATE` по строке задачи. Первый закрывает задачу и пишет `refund:{task_id}`. Остальные видят уже закрытую попытку и журнал не трогают. Уникальный ключ страхует ту же развилку, если когда-нибудь появится второй путь к возврату.

Списание устроено так же, но гонки одинакового ключа там нет: ключ содержит новый `task_id`. Гонка «хватит ли денег и не занят ли лимит» закрывается блокировкой строки пользователя на время подсчёта активных задач, проверки баланса и вставки списания.

`AFTER INSERT`, а не `BEFORE`, потому что у PostgreSQL строковый `BEFORE`-триггер выполняется даже для строки, которую `ON CONFLICT DO NOTHING` потом выбрасывает. Такой триггер начислил бы деньги вхолостую.

## Падение процесса посреди вебхука

Обработчик вебхука делает одно: открывает транзакцию, блокирует задачу, меняет попытку и при необходимости вставляет строку журнала, коммитит. Ответ провайдеру уходит после коммита.

Процесс умер до коммита — PostgreSQL откатывает транзакцию целиком. Нет ни нового статуса, ни строки журнала, ни движения баланса. Провайдер присылает то же тело ещё раз (фейк повторяет доставку на `5xx` и обрыве сети, и умеет прислать два одинаковых тела сразу). Повтор проходит ту же функцию.

Процесс умер после коммита — исход уже в базе. Повторный вебхук видит закрытую попытку и денег не двигает.

Отдельного окна «деньги списались, а статус откатился» нет: строка журнала и статус задачи коммитятся вместе. Триггер баланса живёт внутри этой транзакции.

Отправка к провайдеру устроена как исходящий ящик. Попытка в статусе `sending` коммитится до HTTP. Условный `dispatch_token` позволяет отправить её только одному процессу. Умерли после этого коммита и до ответа клиенту — клиент мог не получить `task_id`, но задача и списание уже лежат в базе. Сторож через `DISPATCH_GRACE_SECONDS` (15 секунд, это дольше HTTP-таймаута в 5 секунд) считает зависшую отправку техническим отказом и ведёт задачу дальше: следующая нога или один возврат. Ту же ногу заново не вызываем, потому что неизвестно, успел ли провайдер её принять. Поздний вебхук по ней обрабатывается по правилу 6.

Сторож запущен в каждом из четырёх воркеров. Общего списка в памяти у них нет. Строку забирает запрос `FOR UPDATE SKIP LOCKED`: три остальных воркера её не видят. Умер воркер внутри этой транзакции — база снимает блокировку, строку подберёт следующий цикл любого живого процесса.

## Правило 6

Поздний `completed` после того, как сторож уже сдал попытку, не должен оставить задачу и с результатом, и с возвратом.

Решение: возврат остаётся, опоздавший файл в задачу не записывается.

Сторож в одной транзакции помечает попытку `timed_out` и либо открывает следующую ногу, либо ставит `failed` и вставляет единственный `refund`. Вебхук, который приходит после этого, берёт ту же блокировку, видит, что попытка уже не открыта, и пишет ссылку только в историю: `late_result_url` и `late_received_at`. `tasks.result_url` и журнал не меняются.

Так сделано, потому что возврат к этому моменту уже мог быть показан пользователю и потрачен. Забирать его обратно — гонка с новыми заказами. Если сторож успел уйти на следующую ногу, файл первой ноги ещё и спорит со второй: вторая может упасть и снова поставить возврат рядом с результатом. Терминальное денежное состояние поэтому липкое. Опоздавший файл не теряется молча: он виден в `GET /tasks/{id}` и по нему тест проверяет, что вебхук дошёл и не стал исходом задачи.

Пока попытка ещё `sending` или `waiting`, `completed` — обычный успех. «Поздно» начинается с момента, когда попытку закрыли, а не по часам.
